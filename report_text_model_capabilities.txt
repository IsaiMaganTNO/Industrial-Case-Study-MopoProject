Figure 1 presents the common end-to-end architecture used across the Mopo demonstrations. The workflow supports two alternative starting points, depending on whether an application is constructed from source datasets or originates from an existing model.

A central element of the architecture is the Interoperable Energy System specification (INES), which provides a common, tool-independent representation of an energy-system model. INES defines a shared structure for describing system components, energy carriers, connections, parameters and temporal information, allowing models originating from different datasets or modelling tools to converge on a consistent intermediate representation. Within the demonstration framework, INES acts as the interface between upstream data and model preparation and the downstream transformation to SpineOpt. It is therefore not an additional optimisation model, but an interoperability layer that decouples the source-data structure from the requirements of the target modelling tool.

In the data-driven pathway, raw datasets are processed by dedicated importers and stored in intermediate data-pipeline databases. These databases contain harmonised information on system components, time series and parameter values while providing inspection points between the original sources and the final model. A model builder then combines the relevant information according to a user configuration, which defines the scope and principal assumptions of the application. The resulting entities, relationships and parameters are written to an INES model database.

In the model-conversion pathway, an existing model database is translated directly from its native structure into INES using a dedicated transformer. This route allows established models to enter the proposed workflow without reconstructing the complete application from raw source data. Once transformed, the resulting INES database can be supplemented with information from additional data pipelines or adjusted through the same model-building and configuration processes where required.

A dedicated transformer maps the INES entities and parameters into a SpineOpt-compatible model database. SpineOpt then executes the optimisation and writes the outputs to a separate results database, preserving a clear distinction between model inputs and optimisation results. Finally, visualisation and post-processing tools extract and aggregate the results for interpretation and reporting.

2.2.	Data and model preparation capabilities 
Data and model preparation within the Mopo demonstration framework follows a modular approach that separates source-data processing from model construction. This separation allows heterogeneous datasets to be handled according to their original structure and subsequently combined into model instances with different geographical scopes and levels of detail. The preparation process covers data import, harmonisation, database storage, spatial and temporal mapping, model configuration and translation into a common interoperable representation.

Dedicated importers are used to process the source datasets required by each application. These importers perform operations such as data cleaning, unit conversion, technology classification, consistency checks and transformation of source-specific fields. The processed information is written to intermediate data-pipeline databases rather than directly to the final optimisation model. These databases provide stable interfaces between the original data sources and the model-construction process, allowing individual datasets to be updated without rebuilding unrelated parts of the application.

Spine Database API provides the programmatic interface through which the importers create, populate and update these databases. The API is used to define entity classes, entities, relationships, parameter definitions, parameter values, alternatives and metadata within the generic Spine data structure. As a result, data originating from different file formats and sectoral conventions can be stored through a consistent interface without requiring pipeline-specific SQL implementations. Spine Database API is also used later by the Model Builder to query the intermediate databases and write the resulting model instance.

The generic data structure accommodates the different parameter formats required by the demonstrations. Scalar values are used for characteristics such as investment costs, efficiencies, technical lifetimes and emission factors. Other parameters are indexed by location, technology, planning period or scenario. Time-dependent information, including electricity demand, renewable capacity factors, hydrological inflows and technology availability, is represented through time series or indexed parameter structures. Relationships among entities retain the connections between technologies, commodities, locations and infrastructure.

Spatial transformations are applied explicitly during data preparation and model construction. Source datasets may refer to countries, administrative regions, electricity-system zones, offshore areas or technology-specific geographical classifications. Mapping definitions connect these spatial structures to the resolution selected for a particular model instance. Additive quantities, such as demand, installed capacity and technical potential, are summed when aggregated and allocated using appropriate weights when disaggregated. Intensive quantities, including efficiencies, costs and capacity factors, are transferred using representative or weighted values. Observed asset locations and sector-specific information are retained where they provide a more reliable allocation basis.

Metadata are preserved alongside the processed information to support traceability. Depending on the source, these metadata may identify the dataset, version, original unit, geographical classification and relevant processing assumptions. Together with the intermediate databases, this allows users to inspect how source information has been transformed before it becomes part of the model. This is particularly important when datasets prepared for different sectors or purposes are combined within the same application.

For applications constructed from component datasets, the Model Builder queries the intermediate databases through Spine Database API and combines the selected information according to a user configuration. This configuration defines the geographical scope, sectors, energy carriers, technologies, planning periods, weather years and spatial resolutions included in the application. The Model Builder applies the relevant mappings and creates the corresponding system components, relationships and parameters in an INES-compliant model database.

The distinction between the Model Builder and INES is important. The Model Builder is the workflow component that selects, aggregates and combines the data, whereas INES defines the structure in which the resulting model is expressed. Consequently, multiple model instances can be generated from the same data-pipeline databases by changing the configuration, without modifying the importers or reconstructing the underlying datasets.

Applications originating from an existing energy-system model enter the preparation process through a dedicated transformer. The transformer maps the native model classes, relationships and parameters to the corresponding INES concepts. Once converted, the model can be supplemented with additional component data or parameters from other pipelines. The data-driven and model-conversion pathways therefore converge in the same interoperable model representation despite having different starting points.

Translation to INES is semantic as well as structural. Source technologies, commodities, networks, storage systems and demands must be interpreted as consistent model components, while preserving their parameter values, units, geographical associations and temporal characteristics. Similar concepts originating from different datasets or native model structures must be represented in the same way before they can be passed to the optimisation layer.

Finally, the output of this process is a complete INES model database that remains independent of the SpineOpt-specific schema. A dedicated transformer subsequently maps the INES components, relationships and parameters into a SpineOpt model database. This final transformation is described here as the boundary of model preparation, while the optimisation features applied after the transformation are discussed in Section 2.4.
2.3.	Workflow and scenario-management capabilities 
Once the model data have been prepared, Spine Toolbox provides the environment for configuring, executing and comparing the demonstration runs. The workflow links the different processing stages, from source-data import and model construction to transformation, optimisation, results extraction and visualisation. These stages are represented as connected project items, making their execution dependencies explicit and allowing the complete modelling process to be repeated from the original inputs.

The modular workflow structure allows individual components to be executed independently during development and validation, while the complete sequence can be run when producing final results. This is particularly useful for large applications, where changes may affect only one dataset, transformation or modelling assumption. Instead of rebuilding every component manually, the affected stage and its downstream dependencies can be re-executed through the same workflow. Intermediate databases also remain available for inspection, helping users identify whether unexpected outcomes originate from the source data, the model-building process, the transformation to SpineOpt or the optimisation results.

Scenario management separates common model data from alternative assumptions. A shared reference dataset defines the system structure and baseline parameter values, while alternatives modify selected parameters or coordinated groups of parameters to represent different demand projections, weather years, technology assumptions, resource availabilities, infrastructure limits, or policy constraints. A scenario then specifies the combination and order of alternatives applied in a particular model run, allowing them to be reused across multiple experiments without creating separate copies of the complete database. This structure makes differences between model runs more transparent and reduces the risk of inconsistencies caused by manually editing multiple versions of the same model.

Not all variations are introduced at the same stage of the workflow. Changes affecting the scope or structure of the model, such as the included geographical areas, sectors, technologies or temporal resolution, are generally defined through the user configuration and applied during model construction. Changes to parameter values within an existing model structure can instead be represented through alternatives and scenarios. This distinction provides flexibility while preserving a clear record of whether a model run differs because of its underlying configuration or because of scenario-specific assumptions.

For every execution, model inputs and optimisation outputs are maintained in separate databases. The input database records the model structure, parameter values and selected alternatives passed to SpineOpt, while the results database contains the corresponding decision variables and model outputs. Consistent naming and storage conventions allow results to be associated with the configuration and scenario that produced them. Post-processing tools can then apply the same aggregation and visualisation methods across runs, supporting direct comparison of investments, dispatch, energy flows, storage operation, emissions and other relevant indicators.

The workflow and scenario-management capabilities therefore provide more than computational automation. They establish a traceable relationship between source data, model configuration, scenario assumptions, optimisation execution and reported results. This is essential for the demonstrations, where the objective is not only to obtain a solution, but also to understand how each model instance was constructed, which assumptions distinguish the analysed cases and whether the results can be reproduced and compared consistently.
2.4.	SpineOpt modelling capabilities used in the demonstrations 
The demonstrations use SpineOpt as a configurable optimisation framework that can be adapted to different geographical scales, temporal structures and decision problems. Rather than relying on separate model formulations, the applications use combinations of SpineOpt features appropriate to their respective purpose. This allows the demonstration portfolio to cover regional and continental capacity-expansion planning, as well as detailed operational analysis, within a common modelling environment.

The generic representation based on nodes, units, connections and storage systems is used to describe energy balances, conversion processes, infrastructure transfers and storage operation. Technologies can connect multiple commodities and geographical areas, allowing interactions among electricity, heat, gases, fuels and other energy or material flows to be represented consistently. The level of sectoral and spatial detail can be adapted to the application without changing the underlying modelling framework.

For the planning applications, SpineOpt jointly optimises investment, retirement and operation over multiple milestone years. Existing and candidate assets are represented together with their technical lifetimes, investment costs, operating characteristics and deployment limits. Investments undertaken in one period can remain available in subsequent periods, enabling the models to examine transition pathways rather than isolated target years by means of the multi-year investment capabilities. Generation, conversion technologies, storage and network infrastructure can therefore be planned simultaneously, together with emissions limits, resource availability and other system-wide constraints.

The planning applications also use blended representative periods to balance operational detail and computational tractability [REFERENCE TO PREVIOUS DELIVERABLE?]. Hourly representative days capture relevant combinations of demand, renewable availability and technology operation, while a lower-resolution representation of the complete year preserves the chronological relationship between seasons. In Mopo, we use the software TulipaClustering.jl [REFERENCE] to identify those representative periods and the number of selected periods is configured by the user. The main advantage of this feature is that changes in storage levels within the representative days are linked to this annual structure, allowing longer-term storage trajectories to be reconstructed. The formulation can consequently distinguish short-duration flexibility, such as battery operation, from the seasonal contribution of hydropower reservoirs, methane storage and hydrogen caverns without requiring a full hourly representation of every planning year [PAPER TNO].

The operational application uses a more detailed representation of electricity-system operation. The relevant SpineOpt capabilities include unit commitment, start-up and shut-down decisions, minimum operating levels, ramping restrictions, reserve provision, transmission constraints and chronological storage operation. Reserve requirements can be represented through dedicated reserve nodes and the relationships between eligible units and reserve products. This allows the provision and activation of reserves to be linked to available unit capacity and system requirements. Where application-specific reserve rules cannot be captured directly through the node structure, user constraints provide an additional mechanism for formulating the required relationships.

SpineOpt’s flexible temporal framework also supports a two-stage operational approach. In the first stage, a lower-resolution optimisation determines the longer-term allocation and trajectory of stored energy. The resulting trajectory is then transferred to a higher-resolution second stage, where storage levels or targets guide a rolling-horizon optimisation. This allows commitment, reserves, network flows and short-term storage operation to be represented in greater detail while maintaining consistency with longer-term storage management.

User constraints complement the standard formulation when a demonstration requires relationships that are specific to its policy, planning or operational context. They can be used for system-wide emissions budgets, resource or infrastructure limits, investment relationships and other application-specific conditions. However, standard model elements are used where the required behaviour can be represented directly, as in the case of reserve products defined through nodes and their associated unit relationships, or the case of emissions using a node to represent the atmosphere.

Taken together, the demonstrations exercise SpineOpt across two complementary dimensions. The planning applications use multi-period investment, sector coupling, blended representative periods and long-duration storage representation at regional and continental scales. The operational application uses chronological dispatch, commitment, reserves, network constraints, a two-stage storage formulation and rolling-horizon optimisation. The precise combination of features, temporal resolution and constraints applied in each model is described in the corresponding demonstration chapters.
